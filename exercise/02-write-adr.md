# งานที่ 2: เขียน ADR สำหรับความต้องการใหม่ (ประมาณ 20 นาที)

> **เชื่อมโยงกับการบรรยาย:** T3 (GPT-4 แบบ zero-shot ให้ผลที่สอดคล้องกัน แต่ *ครบถ้วนน้อยกว่ามนุษย์* ส่วน few-shot ช่วยลดช่องว่างได้มาก), AICH3 (บริบท), สัปดาห์ที่ 10 (message broker)
> **คำถาม:** ADR ที่ AI เขียนดีขึ้นแค่ไหน เมื่อให้ตัวอย่างและบริบทจริงแก่ AI

อ่าน [สถานการณ์ (ภาษาไทย)](../docs/scenario.th.md) ก่อน: ความต้องการ **R-12** ว่าด้วยสิ่งที่เกิดขึ้นหลังจากลูกค้าสั่งซื้อสินค้า

ในแต่ละ run ให้เริ่ม **แชตหรือ session ใหม่** แล้วส่งข้อความด้านล่าง โดยแทนที่ `<paste R-12 here>` ด้วยข้อความ R-12 ภาษาอังกฤษที่อยู่ในกรอบอ้างอิงของ scenario

**Run a: ไม่มีตัวอย่าง (zero-shot)** → [`outputs/2a-adr.md`](outputs/2a-adr.md)
```
Follow prompts/2-write-adr.md
run: a
context: none
requirement: <paste R-12 here>
language: Thai
```

**Run b: มีตัวอย่าง + บริบท** → [`outputs/2b-adr.md`](outputs/2b-adr.md)
```
Follow prompts/2-write-adr.md
run: b
context: docs/scenario.md, docs/adr/0001-use-redis-for-cart-storage.md, system/online-boutique/src/checkoutservice/main.go
requirement: <paste R-12 here>
language: Thai
```

> บรรทัด `language: Thai` ทำให้ agent เขียน ADR เป็นภาษาไทย (หัวข้อของ template และชื่อทางเทคนิคยังคงเป็นภาษาอังกฤษ) หากต้องการภาษาอังกฤษให้ลบบรรทัดนี้ **ใช้ภาษาเดียวกันทั้ง Run a และ Run b** เพื่อให้เปรียบเทียบกันได้

> ใน Run a ให้ตรวจว่า agent ไม่ได้อ่านไฟล์อื่นนอกจาก template จริง ๆ หาก agent เปิด `docs/scenario.md` ให้บันทึกไว้ใน prompt log เพราะจะทำให้การเปรียบเทียบเปลี่ยนไป

## เปรียบเทียบ a กับ b

| เกณฑ์ | Run a | Run b |
|---|---|---|
| ใช้ตัวเลขจาก scenario หรือไม่ (latency, ช่วงพีก, ข้อจำกัดของ MailFast) | ไม่ใช้ตัวเลขเหล่านี้ เพราะ Run a ได้รับเพียงข้อความความต้องการหลังสั่งซื้อ และบอกว่ายังต้องถามข้อมูลเพิ่ม | ใช้ checkout p95 ไม่เกิน 500 ms, ช่วงพีก 200 คำสั่งซื้อ/วินาที และ MailFast p95 1.5 s, p99 8 s, ล้มเหลว 0.5%, ส่งได้ไม่เกิน 50 อีเมล/วินาที |
| ทางเลือกที่พิจารณา (ระบุ) | 1. ให้ขั้นตอนวางคำสั่งซื้อเรียก MailFast, `loyaltyservice` และบริการ analytics โดยตรงแบบ synchronous; 2. ให้ขั้นตอนวางคำสั่งซื้อเผยแพร่เหตุการณ์ `order placed` ผ่านตัวกลางส่งเหตุการณ์ที่เก็บงานได้ แล้วให้ตัวจัดการอีเมล `loyaltyservice` และตัวจัดการ analytics ประมวลผลแยกกัน | 1. ให้ `checkoutservice` เรียก MailFast, `loyaltyservice` และ analytics แบบ synchronous โดยตรง; 2. ให้ `checkoutservice` บันทึกเหตุการณ์ `OrderPlaced` ลง durable outbox แล้วส่งผ่าน RabbitMQ ให้ worker แยกงาน; 3. ให้ `checkoutservice` ส่งงานเข้า durable queue แยกตามระบบปลายทางโดยตรง |
| จัดการแต้มสะสมแบบ "ครั้งเดียวเท่านั้น" และ rate limit ของ MailFast หรือไม่ อย่างไร | พูดถึงการป้องกันงานซ้ำ แต่ยังไม่บอกวิธีให้แต้มเพียงครั้งเดียว และไม่พูดถึงข้อจำกัดการส่งอีเมล | ใช้รหัสคำสั่งซื้อตรวจว่าเคยให้แต้มแล้วหรือยัง และบันทึกผลพร้อมแต้ม; จำกัดการส่งอีเมลไม่เกิน 50 ฉบับ/วินาที แต่ยังรับประกันเวลา 1 นาทีไม่ได้หากบริการแต้มขัดข้องนาน |
| มีสิ่งที่แต่งขึ้นเองหรือไม่ (ตัวเลข เครื่องมือ หรือข้อเท็จจริงที่ไม่มีใน scenario) | ไม่พบตัวเลขที่แต่งขึ้น ตัวกลางส่งงานและตัวรับงาน analytics เป็นสิ่งที่ AI เสนอให้สร้าง ไม่ได้อ้างว่ามีอยู่แล้ว | ตัวเลขตรงกับ scenario; RabbitMQ ถูกกล่าวถึงเพียงว่าทีมเคยใช้ ส่วนที่เก็บงานรอส่ง ตัวรับงาน และคิวสำหรับงานผิดพลาดเป็นข้อเสนอใหม่ ไม่ได้อ้างว่ามีอยู่แล้ว แต่ยังต้องตรวจว่าจะบันทึกคำสั่งซื้อกับงานที่รอส่งพร้อมกันได้อย่างไร |

## รับผิดชอบ ADR ฉบับสุดท้ายของตัวเอง

นิสิตคือสถาปนิก ให้คัดลอก `outputs/2b-adr.md` ไปที่ `docs/adr/0002-<short-title>.md` แล้วแก้ไข**ด้วยตัวเอง**จนพร้อมจะลงชื่อรับรอง ห้ามให้ agent ทำส่วนนี้

- แก้ไขสิ่งที่ผิดหรือแต่งขึ้นเอง และเพิ่มสิ่งที่ขาดหายไป
- ตัดสินใจขั้นสุดท้ายด้วยตัวเอง นิสิตสามารถไม่เห็นด้วยกับ AI ได้

นิสิตจะต้องปกป้อง ADR นี้ต่อหน้าคณะกรรมการรีวิวในส่วน B จึงต้องอธิบายทุกการตัดสินใจใน ADR ได้

| # | สิ่งที่เปลี่ยนจากร่างของ AI | เหตุผล |
|---|---|---|
| 1 | อธิบายว่าต้องเพิ่มที่เก็บข้อมูลถาวรสำหรับคำสั่งซื้อและงานที่รอส่ง และต้องตรวจวิธีบันทึกข้อมูลพร้อมกันก่อนใช้จริง | ร่าง AI ยังไม่รู้ว่าจะเก็บข้อมูลนี้ที่ไหน และโจทย์ไม่ได้ระบุที่เก็บคำสั่งซื้อแบบถาวร (`docs/scenario.md`) |
| 2 | เลือกปรับ `emailservice` เดิมให้ส่งอีเมลผ่าน MailFast | โจทย์ให้เปลี่ยนวิธีส่งอีเมล ไม่ได้บอกให้สร้างบริการอีเมลใหม่ (`docs/scenario.md`, หัวข้อ The new requirement); จึงใช้บริการเดิมเพื่อลดส่วนที่ต้องดูแล |
| 3 | เพิ่มคำอธิบายเรื่องอีเมลค้างในคิวและกรณีให้แต้มไม่ทัน 1 นาที พร้อมสิ่งที่ต้องทดสอบ | ช่วงพีก 200 คำสั่งซื้อ/วินาทีมากกว่าที่ MailFast รับได้ 50 อีเมล/วินาที และต้องให้แต้มภายใน 1 นาที (`docs/scenario.md`, Quality goals and constraints) |
